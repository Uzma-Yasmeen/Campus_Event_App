# Deployment

This guide puts the API, the database and the web client online **without
paying anything**. It takes about 30 minutes end to end.

| Piece | Service | Free tier |
|---|---|---|
| Database | MongoDB Atlas (M0) | 512 MB, no card required |
| API | Render (web service) | Free, no card required |
| Web client | Netlify — or Vercel, or GitHub Pages | Free, no card required |

Check each provider's current terms before signing up; free tiers change.

> **The one catch worth knowing.** Render's free tier puts a service to sleep
> after about 15 minutes without traffic, and the next request has to wait
> roughly 30–60 seconds while it wakes. Everything works, it is just slow on
> the first hit. If you are sending the link to someone, a short note on the
> page — "hosted on a free tier, the first load may take a moment" — saves any
> confusion.

## 1. Database — MongoDB Atlas

1. Create an account at [mongodb.com/atlas](https://www.mongodb.com/atlas), and
   create a free **M0** cluster.
2. **Database Access** → add a database user. Give it a strong password and
   keep it somewhere safe; you will paste it into a connection string shortly.
3. **Network Access** → add IP address → **Allow access from anywhere**
   (`0.0.0.0/0`). Render does not publish fixed outbound IPs, so a narrower
   rule will block the API.
4. **Connect** → **Drivers** → copy the connection string. It looks like:

   ```
   mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority
   ```

   Replace `<user>` and `<password>`, and insert the database name before the
   `?` so the data lands in the right place:

   ```
   mongodb+srv://campus:YOURPASSWORD@cluster0.xxxxx.mongodb.net/campus_events?retryWrites=true&w=majority
   ```

   If the password contains `@`, `:`, `/` or `#`, percent-encode it
   (`@` → `%40`), otherwise the string will not parse.

## 2. API — Render

The repository already contains [`render.yaml`](../render.yaml), so Render can
configure the service itself.

1. Sign up at [render.com](https://render.com) with your GitHub account.
2. **New** → **Blueprint** → pick this repository. Render reads `render.yaml`
   and proposes a service called `campus-events-api`.
3. It will ask for the two values that are deliberately not in the repo:
   - `MONGO_URI` — the Atlas string from step 1
   - `CORS_ORIGINS` — leave it blank for now; you will not have the web
     client's URL until step 3. Set it straight afterwards.
4. Deploy. The first build takes a few minutes.

`JWT_SECRET` is generated by Render automatically. Do not paste your local one.

When it is live, check:

```bash
curl https://campus-events-api.onrender.com/api/health
# {"status":"ok","uptime":12.34}
```

Then seed the institution list, using Render's **Shell** tab:

```bash
npm run seed
```

### Doing it manually instead

If you would rather not use the blueprint: **New** → **Web Service**, then set
root directory `backend`, build command `npm ci`, start command `npm start`,
health check path `/api/health`, and add `NODE_ENV=production`,
`TRUST_PROXY=1`, `JWT_SECRET`, `MONGO_URI` and `CORS_ORIGINS` by hand.

## 3. Web client — Netlify

The web client is static files with no build step.

1. Sign up at [netlify.com](https://netlify.com).
2. **Add new site** → **Import an existing project** → this repository.
3. Set **publish directory** to `web`. Leave the build command empty.
4. Deploy. You will get a URL such as
   `https://campus-events.netlify.app`.

### Point it at the API

The web client defaults to `http://localhost:5000/api`, which will not work in
production. There is exactly one line to change, in
[`web/assets/config.js`](../web/assets/config.js):

```js
window.CAMPUS_API_BASE = 'https://campus-events-api.onrender.com/api';
```

Keep the trailing `/api`. Commit and push; Netlify redeploys automatically.

### Then close the CORS loop

Go back to Render → your service → **Environment**, and set:

```
CORS_ORIGINS=https://campus-events.netlify.app
```

No trailing slash. Save; Render redeploys. Until this is set, the browser will
refuse every API call from the deployed site — that is the allowlist doing its
job, not a bug.

## 4. Mobile app

The mobile app is not published to an app store here. To run it against the
deployed API, set the base URL in [`mobile/app.json`](../mobile/app.json):

```json
{
  "expo": {
    "extra": { "apiBaseUrl": "https://campus-events-api.onrender.com/api" }
  }
}
```

Then `npm start` and open it in Expo Go, or `npm run web` for a browser.

## What is already handled

The backend is production-ready in these respects:

- **CORS allowlist** — enforced when `NODE_ENV=production`; requests without an
  `Origin` header (curl, the mobile app) still pass, since the browser
  same-origin rules do not apply to them
- **Rate limiting** — 10 failed sign-ins per 15 minutes, 10 new accounts per
  hour, 60 uploads per hour, 500 API requests per 15 minutes. Successful
  sign-ins are not counted, so normal use never hits the limit
- **Security headers** via helmet, and `X-Powered-By` removed
- **Response compression**
- **Graceful shutdown** on `SIGTERM`, so in-flight requests finish when the
  platform recycles the instance
- **Startup validation** — the process refuses to boot without `MONGO_URI`, or
  without `JWT_SECRET` in production, rather than failing confusingly later
- **Error messages** — internal 500 text is never returned to clients in
  production

## The one real limitation: uploaded files

Render's free tier gives the service an **ephemeral filesystem**. Everything
written to disk is lost when the instance restarts or wakes from sleep.

**QR codes handle this already.** A generated code is derived from data still
held in MongoDB, so if the file is missing when it is requested, the API
rebuilds it on the spot and serves it. Nothing breaks, and no configuration is
needed.

**Cover images, avatars and uploaded QR codes cannot be rebuilt** — they only
ever existed as uploaded bytes. On an ephemeral disk they will disappear on the
next restart. In practice this means a demo keeps working but loses pictures
that visitors added.

Three ways to handle it, depending on how much it matters:

1. **Accept it.** Fine for a portfolio demo. Events, registrations, accounts
   and QR codes all persist, because they live in MongoDB.
2. **Attach a persistent disk.** Render offers one on paid plans. Mount it at
   `backend/uploads` and the problem disappears with no code change.
3. **Move uploads to object storage** — Cloudinary's free tier or an S3 bucket.
   This is the right answer for real use. The upload path is isolated in
   [`backend/utils/upload.js`](../backend/utils/upload.js), so swapping the
   multer storage engine is a contained change.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Site loads, every API call fails in the browser console | `CORS_ORIGINS` not set, or has a trailing slash / wrong protocol |
| `MongoServerError: bad auth` | Password wrong, or special characters not percent-encoded |
| Requests hang, then fail | Atlas **Network Access** does not allow `0.0.0.0/0` |
| First request takes ~50 seconds | Free tier cold start. Expected |
| `429 Too many attempts` while testing | Rate limiter. Wait 15 minutes, or lower the limits in `backend/middleware/rateLimit.js` |
| Deploy succeeds but no institutions listed | Run `npm run seed` in Render's Shell |
| Everyone gets rate-limited together | `TRUST_PROXY` not set to `1` |
